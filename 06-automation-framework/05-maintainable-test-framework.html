Maintainable Test Framework

Liên quan: Mục lục · Trước: Configuration · Practice: Mini project · Phỏng vấn

🎯 Learning Objectives

Sau bài này bạn có thể:

  • Đánh giá Selenium1 theo tiêu chí dễ bảo trì
  • Áp dụng 10 nguyên tắc
  • Review code test bằng checklist
  • Lập backlog cải thiện theo thứ tự giá trị/công sức

📋 Prerequisites

  • Architecture
  • Reusable Components

1. "Dễ bảo trì" nghĩa là gì?

Một framework dễ bảo trì khi:

  1. UI đổi nhỏ ⇒ sửa ở một chỗ.
  2. Người mới đọc test hiểu ngay.
  3. Thêm test mới nhanh (dùng lại).
  4. Test fail ⇒ biết vì sao trong vài phút.
  5. Chạy ổn định (ít flaky).
  6. Máy nào chạy cũng giống nhau (Wrapper, ghim phiên bản, cấu hình trong Git).

2. Đánh giá Selenium1 theo tiêu chí

Tiêu chí Hiện trạng Điểm
Tái lập build Wrapper + phiên bản ghim + .gitignore đúng 🟢 Tốt
Đồng bộ hoá Explicit Wait nhất quán, không sleep, không implicit 🟢 Tốt
Độc lập test Mỗi test một browser 🟢 Tốt
Assertion Có message, kiểm chứng trước/sau 🟢 Tốt
Locator tập trung Rải trong test 🟡 Cần POM
Cấu hình/dữ liệu Hard-code 🟡 Cần Config/DataProvider
Chẩn đoán lỗi Không screenshot/log có cấu trúc 🟡
Tái sử dụng Helper private trong từng class 🟡
Song song / đa browser Không ⚪ Chưa cần
CI Chưa có ⚪ Chưa cần

Với mục đích học tập 10 bài đầu, kết quả này rất tốt. Danh sách 🟡 là backlog học tập.

3. Mười nguyên tắc

  1. Test độc lập — không phụ thuộc thứ tự/dữ liệu của test khác.
  2. Mỗi test một mục tiêu — tên mô tả hành vi: shouldShowErrorWhenPasswordInvalid.
  3. Không Thread.sleep — chờ theo điều kiện.
  4. Locator ổn định, tập trung (Page Object).
  5. Assertion ở test, hành vi ở page.
  6. Cấu hình/dữ liệu ngoài code.
  7. Fail rõ ràng — message, ảnh, log.
  8. Giữ test nhanh — không làm điều không cần (ví dụ đăng nhập qua UI cho mọi test: dùng cookie/API setup).
  9. Phiên bản được ghim — Wrapper, thư viện, plugin.
  10. Refactor liên tục — đừng để helper lặp ≥ 3 lần.

4. Đặt tên

Đối tượng Quy ước Ví dụ
Test class <Chức năng>Test LoginTest
Test method Động từ + kỳ vọng shouldLoginWithValidCredentials
Page class <Trang>Page LoginPage
Method hành động Động từ loginAs, addElement
Method lấy dữ liệu get..., is... getFlashMessage, isAtSecureArea
Hằng UPPER_SNAKE LOGIN_URL (🧩 dự án)
Package chữ thường pages, tests, base (🧩)

🧩 Dự án đặt tên Exercise01_LoginTest theo đề bài (học tập). Dự án thật thường đặt theo chức năng, không theo số thứ tự.

5. Quản lý thay đổi UI

Thay đổi Cách ứng phó
Đổi id/class Sửa 1 dòng trong Page
Đổi luồng (thêm bước xác nhận) Sửa method nghiệp vụ trong Page; test giữ nguyên
Đổi chữ hiển thị Dùng locator không phụ thuộc text; hoặc tách text ra hằng
Đổi cấu trúc DOM CSS ngắn, ít lồng; data-testid do dev thêm
Thêm popup/cookie banner Xử lý ở BasePage/BaseTest một lần

Mẹo lớn: thoả thuận với dev thêm data-testid cho phần tử quan trọng.

6. Giảm flaky

Xem selenium/10. Tóm tắt: Wait đúng điều kiện (đặc trưng cho trạng thái mới, như 🧩 Ex10 textToBe), tránh phụ thuộc animation, cô lập dữ liệu, ổn định môi trường, kích thước cửa sổ cố định, không che flaky bằng retry.

7. Review code test

Checklist khi review PR:

  • Test có assertion có ý nghĩa?
  • Wait đúng điều kiện, không sleep?
  • Locator ổn định, nằm trong Page?
  • Không dữ liệu/URL/bí mật hard-code sai chỗ?
  • Test độc lập, chạy lẻ được?
  • clean test xanh, Tests run đúng?
  • Không commit target/, .mvn/repository/?
  • pom.xml đổi có lý do?

8. Tài liệu hoá

  • README.md: yêu cầu môi trường, cách chạy (🧩 dự án có README tốt).
  • Quy ước đặt tên/ cấu trúc package.
  • Cách thêm Page/Test mới.
  • Cách đọc báo cáo.
  • Cách xử lý sự cố (maven/08).

9. Lộ trình cải thiện Selenium1 (đề xuất theo thứ tự giá trị/ công sức)

Ưu tiên Việc Công sức Giá trị
1 Chụp screenshot khi fail Thấp Cao
2 Thêm ChromeOptions + headless qua -D Thấp Cao (CI)
3 Tách Config Thấp Trung
4 POM cho Login, Dropdown, Tables Trung Cao
5 @DataProvider cho login nhiều case Thấp Trung
6 Logging (slf4j-simple) Thấp Trung
7 CI chạy ./mvnw -B clean test Trung Cao
8 ThreadLocal + parallel Trung Trung
9 Báo cáo Extent/Allure Trung Trung

Làm từng bước nhỏ, mỗi bước chạy clean test xanh rồi mới commit.

Tóm tắt

Framework tốt = ít lặp, ít bất ngờ, dễ chẩn đoán, dễ đổi. Bắt đầu nhỏ như Selenium1, thêm tầng khi nhu cầu xuất hiện.

💼 Interview Corner

1. What makes a test framework maintainable?

  • 🇻🇳 Dịch: Điều gì làm framework dễ bảo trì?
  • Suggested answer (EN): Locators in one place, independent and readable tests, condition-based waits, externalized config and data, clear failure evidence and reproducible builds with pinned versions.
  • Giải thích (VI): 10 nguyên tắc.
  • Follow-up: How do you review test code?

2. What would you improve first in a small framework?

  • 🇻🇳 Dịch: Cải thiện gì đầu tiên?
  • Suggested answer (EN): Add screenshots on failure and headless support for CI, then extract configuration and introduce page objects, each as a small verified change.
  • Giải thích (VI): Ưu tiên giá trị/công sức.
  • Follow-up: Why small changes?

📌 Lesson Summary

Kiến thức cần nhớ

  • Locator tập trung, test độc lập, chờ theo điều kiện
  • Cấu hình/ dữ liệu ngoài code
  • Backlog theo giá trị/công sức

Method / lệnh cần biết

  • Checklist review PR, quy ước đặt tên

Điểm dễ nhầm lẫn

  • Bảo trì ≠ nhiều tính năng
  • Retry ≠ sửa flaky
  • Refactor mỗi bước phải clean test xanh
