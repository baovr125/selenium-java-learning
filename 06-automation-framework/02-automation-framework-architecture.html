📋 Prerequisites

  • Page Object Model

1. Framework là gì?

Automation Framework = bộ khung quy ước + mã dùng chung để viết test nhất quán, dễ bảo trì, dễ mở rộng. Không chỉ là "một đống test": nó quyết định driver được tạo ở đâu, locator đặt đâu, cấu hình đọc từ đâu, báo cáo ghi thế nào.

2. Các tầng của framework

text
┌──────────────────────────────────────────────────────────────────┐
│ 1. Test layer         tests/*Test.java        (kịch bản + assert) │
├──────────────────────────────────────────────────────────────────┤
│ 2. Page layer         pages/*Page.java        (hành vi trang)     │
├──────────────────────────────────────────────────────────────────┤
│ 3. Core layer         BasePage, BaseTest, DriverFactory, Waits    │
├──────────────────────────────────────────────────────────────────┤
│ 4. Support layer      Config, TestData, Utils, Logger, Screenshot │
├──────────────────────────────────────────────────────────────────┤
│ 5. Infrastructure     Selenium, TestNG, Maven/mvnw, CI, Reports   │
└──────────────────────────────────────────────────────────────────┘

Quy tắc phụ thuộc: tầng trên gọi tầng dưới, không ngược lại (Page không biết Test; Core không biết Page cụ thể).

3. Đối chiếu với Selenium1

Thành phần Có trong dự án? File
Test layer ✅ src/test/java/tests/*
Base Test (setup/teardown) ✅ BaseTest
Page layer / Base Page ❌ —
Driver Factory ❌ (new ChromeDriver() trực tiếp) —
Configuration Manager ❌ (hằng hard-code) —
Test data ❌ (trong test) —
Utility classes ◐ (helper private trong từng test: scrollToBottom, getRowData, assertSameElement) các Exercise
Logging ◐ (System.out.println) các Exercise
Reporting ✅ mặc định (Surefire/TestNG HTML) target/surefire-reports/
Screenshot khi fail ❌ —
Test execution config ✅ testng.xml, pom.xml
Dependency management ✅ pom.xml, Wrapper

Điều đáng giá: các helper private trong từng Exercise (ví dụ getRowData, scrollToBottom) chính là mầm của Utility/Page method — khi bị lặp ở ≥ 2 nơi thì kéo ra chỗ dùng chung.

4. Cấu trúc thư mục đề xuất

text

├── base/

├── core/
│   ├── DriverFactory.java            # tạo WebDriver theo cấu hình

├── config/
│   └── Config.java                   # đọc config.properties/-D
├── pages/
│   ├── BasePage.java
│   ├── LoginPage.java
│   └── ...
├── data/
│   └── LoginData.java                # record/POJO dữ liệu
├── utils/
│   ├── Screenshots.java
│   └── Log.java
├── listeners/
│   └── TestListener.java             # chụp ảnh khi fail, ghi report
└── tests/
    └── LoginTest.java ...
src/test/resources/
├── config.properties
└── testdata/login.csv

5. Các thành phần liên kết với nhau như thế nào

text
testng.xml ─► Surefire ─► TestNG ─► (đọc) TestListener
                             │
                             ▼
                        BaseTest.setup()
                          ├─ Config  ◄── config.properties / -Dbrowser=...
                          ├─ DriverFactory.create(browser) ──► WebDriver (ThreadLocal)
                          └─ WebDriverWait(timeout từ Config)
                             │
                             ▼
                        LoginTest.@Test
                          ├─ new LoginPage(driver) ─ extends BasePage ─ (wait, click, type)
                          ├─ Page trả dữ liệu ──► Assert (TestNG)
                          └─ DataProvider ◄── TestData (CSV/JSON)
                             │
                             ▼
                        BaseTest.tearDown(result)
                          ├─ nếu fail: Screenshots.take(driver) ──► target/screenshots/
                          └─ driver.quit()

Luồng một lần chạy ./mvnw clean test:

  1. mvnw (Wrapper) ⇒ đúng Maven 3.9.16.
  2. Maven phân giải dependency theo pom.xml ⇒ biên dịch src/test.
  3. Surefire đọc testng.xml ⇒ TestNG tạo test.
  4. Với mỗi test: setup() → test (qua Page) → tearDown().
  5. Kết quả ghi vào target/surefire-reports/.

6. Nguyên tắc thiết kế

Nguyên tắc Ý nghĩa Ví dụ
Separation of Concerns Mỗi lớp một trách nhiệm Test = kịch bản; Page = cách thao tác
DRY Không lặp BasePage.click dùng lại
Single Source of Truth Một nơi định nghĩa URL, timeout ở Config
Composition over Inheritance Ưu tiên ghép thành phần Page có Header
Fail fast, fail clear Lỗi sớm và rõ Message assert; kiểm tra config
Independent tests Test không phụ thuộc nhau @BeforeMethod mở browser mới
Convention over configuration Quy ước tên/vị trí *Test, *Page

7. Mức độ "vừa đủ"

Đừng dựng framework khổng lồ cho 10 test. Gợi ý:

Quy mô Nên có
≤ 10 test, học tập (🧩 hiện tại) BaseTest, test rõ ràng, Explicit Wait
10–50 test + Page Object, BasePage, Config
50+ test, nhóm + DriverFactory, DataProvider, Listener, Logging, Report, CI, parallel

YAGNI (You Aren't Gonna Need It): chỉ thêm khi có nhu cầu thật.

8. Rủi ro khi thiết kế framework

Rủi ro Biểu hiện Cách tránh
Over-engineering Nhiều lớp trừu tượng không dùng Bắt đầu nhỏ, refactor khi lặp
Tight coupling Sửa 1 chỗ vỡ nhiều chỗ Tách tầng
Framework "magic" Người mới không hiểu Tài liệu + ví dụ
Không version hoá cấu hình "Máy tôi chạy" pom.xml, Wrapper, config trong Git
Test phụ thuộc môi trường ngoài Flaky Dữ liệu ổn định; Wait đúng

💼 Interview Corner

1. Describe the architecture of an automation framework.

  • 🇻🇳 Dịch: Mô tả kiến trúc automation framework.
  • Suggested answer (EN): Layers of tests, page objects, core utilities such as base classes and driver factory, support services like config and reporting, and infrastructure such as Selenium, TestNG, Maven and CI, with dependencies flowing downward.
  • Giải thích (VI): Có sơ đồ.
  • Follow-up: How big should a framework be?

2. How do components of your framework interact?

  • 🇻🇳 Dịch: Các thành phần liên kết thế nào?
  • Suggested answer (EN): TestNG runs the tests; BaseTest creates the driver using config; tests use page objects that extend BasePage for waits and actions; teardown captures evidence and quits.
  • Giải thích (VI): Luồng một lần chạy.
  • Follow-up: Where do screenshots fit?
