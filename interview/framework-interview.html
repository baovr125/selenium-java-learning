Testing Framework và Page Object Model — Interview

Song ngữ Anh–Việt. Cấu trúc mỗi câu: Câu hỏi → Dịch → Câu trả lời mẫu → Giải thích → Ví dụ thực tế → Câu hỏi đào sâu. Quay lại: Interview README

Phần 1 — TestNG và JUnit

Q1. What is TestNG and why use it with Selenium?

Dịch: TestNG là gì, vì sao dùng với Selenium?

Sample answer: TestNG is a Java testing framework that organizes and runs tests. It offers annotations, grouping, dependencies, data providers, parallel execution, XML suite configuration and HTML reports. Selenium drives the browser; TestNG manages test lifecycle and results.

Giải thích: Selenium không có test runner.

Ví dụ: Dự án dùng TestNG 7.10.2 với testng.xml liệt kê 10 class.

Đào sâu: Can Selenium run without TestNG? → Có (dùng main() như run-test.ps1), nhưng thiếu runner/báo cáo.

Q2. Explain the TestNG annotation execution order.

Dịch: Thứ tự chạy annotation?

Sample answer: @BeforeSuite, @BeforeTest, @BeforeClass, @BeforeMethod, the @Test, then @AfterMethod, @AfterClass, @AfterTest, @AfterSuite.

Giải thích: Setup từ ngoài vào trong; teardown ngược lại.

Ví dụ: BaseTest dùng @BeforeMethod/@AfterMethod ⇒ mỗi test một Chrome (~91 s cho 10 test).

Đào sâu: When would you use @BeforeClass? → nhanh hơn, đổi lại test dễ ảnh hưởng nhau.

Q3. What is testng.xml and what do <suite>, <test> and <class> mean?

Dịch: testng.xml là gì?

Sample answer: It is the configuration of what to run. A <suite> contains one or more <test> blocks; each <test> contains classes, packages, methods or groups. A <test> block is not a single test method.

Giải thích: Nhầm lẫn kinh điển.

Ví dụ: Suite "Selenium Getting Started" → test "Exercises 1-10" → 10 class.

Đào sâu: How does Maven use it? → Surefire suiteXmlFile trong pom.xml.

Q4. What is a DataProvider?

Dịch: DataProvider là gì?

Sample answer: A method annotated with @DataProvider that returns Object[][]; each row runs the test once with that row's arguments. It enables data-driven testing, for example multiple login credentials. It can read from CSV, JSON or Excel.

Giải thích: Mỗi hàng chạy cả @BeforeMethod/@AfterMethod.

Ví dụ: Login hợp lệ/không hợp lệ cho Ex1 (đề xuất cải tiến).

Đào sâu: Parallel data provider? → parallel = true.

Q5. What is the difference between hard assert and soft assert?

Dịch: Hard assert khác soft assert?

Sample answer: A hard assert stops the test at the first failure. A soft assert records failures and continues, and I must call assertAll() at the end, otherwise the test never fails.

Giải thích: Soft cho nhiều kiểm tra độc lập.

Ví dụ: Dự án dùng hard assert (Assert.assertEquals...).

Đào sâu: Pitfall of soft assert? → quên assertAll().

Q6. What are groups and how do you run them?

Dịch: Groups là gì, chạy thế nào?

Sample answer: Groups label tests, for example smoke and regression. I select them in testng.xml using <groups><run><include name="smoke"/>. This lets CI run a fast smoke suite on every commit and the full regression nightly.

Giải thích: Với Maven: suite XML riêng; chú ý -Dtest bỏ qua XML.

Ví dụ: Ex1 + EnvironmentCheck là smoke; còn lại regression.

Đào sâu: Alternative in JUnit 5? → @Tag.

Q7. How do you run tests in parallel with TestNG and Selenium?

Dịch: Chạy song song?

Sample answer: Set parallel (methods, classes or tests) and thread-count in testng.xml. Each thread needs its own WebDriver, so I store it in a ThreadLocal<WebDriver> and never use a static driver.

Giải thích: Driver không thread-safe.

Ví dụ: BaseTest hiện dùng field instance, chạy tuần tự.

Đào sâu: What do you do in teardown with ThreadLocal? → remove().

Q8. TestNG vs JUnit 5 — main differences?

Dịch: Khác biệt chính?

Sample answer: TestNG has testng.xml suites, groups, dependsOnMethods and @DataProvider; JUnit 5 has @Tag, @ParameterizedTest and a modular platform. Lifecycle annotations differ: @BeforeMethod vs @BeforeEach. Also assertion argument order differs: TestNG (actual, expected), JUnit (expected, actual).

Giải thích: Bảng ở testing-framework/02.

Ví dụ: Dự án dùng TestNG, không có JUnit.

Đào sâu: Which would you choose for a new project? → theo chuẩn của nhóm; nhất quán quan trọng hơn.

Q9. Why does mvnw test run only 10 tests though there are 11 test classes?

Dịch: Vì sao mvnw test chạy 10 test dù có 11 class?

Sample answer: The Surefire plugin is configured with suiteXmlFile = testng.xml, which lists 10 classes. EnvironmentCheckTest is not listed, so it is only run with -Dtest=EnvironmentCheckTest (which makes Surefire ignore the suite file) or through the script.

Giải thích: Câu hỏi kiểm tra bạn hiểu cấu hình thực tế — đã kiểm chứng.

Ví dụ: .\mvnw.cmd test "-Dtest=EnvironmentCheckTest" ⇒ Tests run: 1.

Đào sâu: How would you add it to smoke? → thêm vào XML hoặc groups.

Q10. What causes tests to be skipped in TestNG?

Dịch: Nguyên nhân test bị skipped?

Sample answer: A failed @BeforeMethod/configuration method, a failed dependency with dependsOnMethods, or a SkipException. Skipped tests do not fail the Maven build, so I always check the Skipped count.

Giải thích: BUILD SUCCESS không có nghĩa mọi test đã chạy.

Ví dụ: Nếu setup() không tạo được Chrome, các test sau có thể skipped.

Đào sâu: How do you get skipped counted as failure? → kiểm tra trong CI.

Phần 2 — Page Object Model

Q1. What is the Page Object Model and why use it?

Dịch: POM là gì, vì sao dùng?

Sample answer: POM is a design pattern where each page, or part of a page, is a class that holds its locators and exposes actions. Tests use these actions instead of locators. When the UI changes I update one class, not every test, and tests become readable.

Giải thích: Tách "cái gì" (test) khỏi "như thế nào" (page).

Ví dụ: Dự án chưa dùng POM: locator nằm trong test (Ex1). Nếu đổi id="username" phải sửa mọi nơi dùng.

Đào sâu: Disadvantages? → tốn công ban đầu, dễ thành "God Page".

Q2. How do you design a page class?

Dịch: Thiết kế page class?

Sample answer: One class per page or component. Locators are private By fields. Public methods represent user actions and return either the next page object or data. The class receives WebDriver in the constructor and extends a BasePage with common wait, click and type helpers. Assertions stay in the test.

Giải thích: Quy tắc chi tiết ở framework-design/01.

Ví dụ: LoginPage.loginAs(user, pass) trả SecureAreaPage.

Đào sâu: Why return the next page? → luồng rõ, kiểm tra điều hướng.

Q3. Should page objects contain assertions?

Dịch: Page có chứa assertion không?

Sample answer: Generally no. The page returns data or state, like getFlashMessage(), and the test asserts. This keeps pages reusable for different scenarios, including negative ones. A small isLoaded() check is acceptable.

Giải thích: Assertion trong Page làm Page gắn với một kịch bản.

Ví dụ: Assert.assertTrue(secure.getFlashMessage().contains("You logged into a secure area!")) đặt ở test.

Đào sâu: What about waiting inside pages? → có, trong BasePage.

Q4. By fields vs @FindBy with PageFactory?

Dịch: By hay @FindBy?

Sample answer: I prefer By fields: simple, no initialization, and the element is found fresh on each use, which avoids stale elements. @FindBy with PageFactory.initElements creates lazy proxies; it is common in older code but harder to debug.

Giải thích: Cả hai đều dùng được; nhất quán trong dự án.

Ví dụ: private final By usernameInput = By.id("username");.

Đào sâu: Is PageFactory deprecated? → Vẫn có trong Selenium 4 nhưng ít được khuyến khích; hãy kiểm tra ghi chú phiên bản bạn dùng.

Q5. How do you connect page classes with test classes?

Dịch: Kết nối Page với Test?

Sample answer: BaseTest creates and quits the driver. A test creates a page with new LoginPage(driver) and calls its actions. Page objects do not store test state, so they are cheap to create.

Giải thích: Driver sinh ở BaseTest, truyền xuống Page.

Ví dụ: new LoginPage(driver).open().loginAs("tomsmith", "SuperSecretPassword!").

Đào sâu: With parallel execution? → ThreadLocal driver.

Q6. What are common POM design mistakes?

Dịch: Lỗi thiết kế POM thường gặp?

Sample answer: Assertions inside pages, public locators, one huge page class, low-level methods instead of business actions, Thread.sleep in pages, storing WebElement as long-lived fields, and repeated locators across pages instead of shared components.

Giải thích: Bảng ở framework-design/01.

Ví dụ: Header chung nên là component riêng.

Đào sâu: How do you model a shared header? → class Header là field của Page (composition).

Q7. How would you apply POM to the Dynamic Controls exercise?

Dịch: Áp dụng POM cho Exercise 10?

Sample answer: A DynamicControlsPage with private locators for the checkbox, input, buttons and message. Methods removeCheckbox() and enableInput() click and wait for the exact message with textToBe; getters like getMessage() and isInputEnabled(). The test asserts the message and state.

Giải thích: Wait nằm trong Page, test sạch.

Ví dụ: Bám theo Exercise10_DynamicControlsTest: textToBe(messageLocator, "It's enabled!").

Đào sâu: Why textToBe rather than visibility? → thông báo cũ "It's gone!" vẫn đang hiện.

Q8. When is POM overkill?

Dịch: Khi nào POM là quá mức?

Sample answer: For tiny throwaway scripts or very few tests, a simple helper may be enough. POM pays off when there are many tests that share pages and the UI changes. I start simple and introduce POM when locators and steps start repeating.

Giải thích: YAGNI — thể hiện trưởng thành kỹ thuật.

Ví dụ: 10 bài mỗi bài một trang riêng: POM chưa bắt buộc, nhưng là bước học tiếp theo hợp lý.

Đào sâu: What is your refactoring trigger? → lặp lần thứ ba.
