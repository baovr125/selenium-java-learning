Automation Concepts — Interview (lý thuyết tự động hoá)

Song ngữ Anh–Việt. Cấu trúc mỗi câu: Câu hỏi → Dịch → Câu trả lời mẫu → Giải thích → Ví dụ → Câu hỏi đào sâu. Quay lại: Interview README Nhóm câu "tư duy automation" mà interviewer dùng để phân biệt người biết dùng công cụ với người hiểu vì sao. Không cần chạy code để học — chỉ cần hiểu và nói được.

AC1. What is test automation? What are its benefits and limits?

Dịch: Tự động hoá kiểm thử là gì; lợi ích và giới hạn?

Sample answer: Test automation uses scripts and tools to execute tests and compare actual results with expected results without manual effort. Benefits: fast and repeatable regression, earlier feedback in CI, consistent execution. Limits: high initial and maintenance cost, it only checks what it is told to check, and it cannot judge usability or exploratory aspects. It complements manual testing and does not replace it.

Giải thích: Nêu cả hai mặt. Câu trả lời "automation thay thế manual" là dấu hiệu thiếu kinh nghiệm.

Ví dụ: Dự án Selenium1: 10 test chạy ~91 s lặp lại được; nhưng "giao diện có dễ dùng không" vẫn phải kiểm tra thủ công.

Đào sâu: Which tests would you never automate? → kiểm tra một lần, UI thay đổi liên tục, đánh giá chủ quan.

AC2. What is the test pyramid? Why fewer UI tests?

Dịch: Test pyramid là gì? Vì sao UI test ít hơn?

Sample answer: The pyramid suggests many fast unit tests at the base, fewer integration or API tests in the middle, and few UI end-to-end tests at the top. UI tests are slower, more fragile because of the browser and timing, and costlier to maintain, so I keep them for critical user flows and verify business logic at lower levels.

Giải thích: Liên hệ kiến thức API/SQL của bạn: kiểm tra logic ở API, UI chỉ kiểm tra luồng người dùng.

Ví dụ: Đăng nhập để chuẩn bị dữ liệu bằng API, rồi chỉ dùng UI cho bước cần kiểm tra.

Đào sâu: Is the pyramid always right? → Là hướng dẫn, không phải luật; tuỳ kiến trúc hệ thống.

AC3. How do you decide what to automate?

Dịch: Quyết định tự động hoá cái gì?

Sample answer: I automate scenarios that are repetitive, stable, high-value or regression-prone, with a clear expected result and data I can control. I start with smoke tests of critical flows. I avoid one-off checks, rapidly changing UI and subjective checks. I weigh the cost of writing and maintaining the test against the manual effort it saves.

Giải thích: Có tiêu chí + có ROI.

Ví dụ: Phase 8/01: bảng S1–S12, S12 "trông đẹp/dễ dùng" không tự động hoá.

Đào sâu: How do you measure ROI? → so sánh thời gian chạy tay lặp lại với chi phí viết + bảo trì + thời gian sửa flaky.

AC4. What types of automation frameworks do you know?

Dịch: Các loại automation framework?

Sample answer: Linear (record and playback, scripts top to bottom), modular (reusable functions per module), data-driven (test logic separated from data, for example TestNG @DataProvider), keyword-driven (actions described by keywords in tables), hybrid (a mix), and behavior-driven (Gherkin scenarios, for example Cucumber). My own project is a hybrid of modular and data-driven using Page Objects and TestNG.

Giải thích: Chỉ cần nêu đúng tên và đặc trưng; nói rõ bạn đã dùng loại nào.

Ví dụ: Page Object + @DataProvider + testng.xml.

Đào sâu: When is BDD worth it? → khi cần cộng tác với BA/PO viết kịch bản; thêm chi phí duy trì.

AC5. Which design patterns are used in automation frameworks?

Dịch: Design pattern thường dùng trong framework?

Sample answer: Page Object Model separates locators and page actions from tests. Factory creates the right driver from configuration, for example a DriverFactory. Singleton or a static holder gives one access point for configuration, but I avoid sharing a single WebDriver between threads. Builder or fluent style can make test data and page calls readable. Facade can hide a multi-step flow such as "login".

Giải thích: Nói được vấn đề mỗi pattern giải quyết, không chỉ tên.

Ví dụ: DriverFactory.create(browser, headless); LoginPage.open().loginAs(...) trả về Page kế tiếp.

Đào sâu: Why is a Singleton WebDriver risky? → không an toàn luồng, test nhiễm trạng thái của nhau.

AC6. What causes flaky tests, and how do you deal with them?

Dịch: Nguyên nhân test flaky và cách xử lý?

Sample answer: Common causes: synchronization (not waiting for the right condition), unstable locators, shared or changing test data, tests depending on each other or on order, environment differences such as speed and browser version, and real intermittent bugs. My approach: reproduce by rerunning, read the exact exception, replace fixed sleeps with a condition specific to the new state, make tests independent and data controlled, then rerun many times. I use retry only as a temporary measure with tracking, because it hides the root cause.

Giải thích: Câu then chốt của vòng Selenium — phải có quy trình, không chỉ "tăng timeout".

Ví dụ: Exercise 10: thông báo cũ vẫn hiển thị ⇒ dùng textToBe; Exercise 7: testng-failed.xml ghi lại lần flaky thật.

Đào sâu: Is retry on failure a good solution? → chỉ là biện pháp tạm; che nguyên nhân gốc, làm mất niềm tin vào bộ test.

AC7. How do you manage test data?

Dịch: Quản lý dữ liệu kiểm thử thế nào?

Sample answer: I keep data out of the test logic: simple values in config.properties or a data file (CSV/JSON), multiple input sets through @DataProvider. Tests should create or reset the data they need so they are independent. Credentials must not be committed; I read them from environment variables or system properties. For stateful systems I prepare data through API or database setup instead of the UI.

Giải thích: Kết hợp kiến thức API/SQL: setup/cleanup bằng API/SQL.

Ví dụ: Dự án hiện hard-code tomsmith/SuperSecretPassword! (trang demo công khai) — 00-project-analysis mục 10 #5 đề xuất tách ra.

Đào sâu: How do you avoid tests interfering through shared data? → dữ liệu riêng cho mỗi test hoặc dọn dẹp sau test.

AC8. What makes an automation failure report useful? What do you log?

Dịch: Báo cáo lỗi automation thế nào là hữu ích?

Sample answer: It states which test failed, the exact exception and message, the step, the environment (browser, version, build), and evidence such as a screenshot and relevant logs. The timeout message should describe the condition that was awaited. I separate "test failed because the product is wrong" from "test failed because the script is wrong" before reporting a bug.

Giải thích: Phân loại lỗi sản phẩm vs lỗi script — kỹ năng quan trọng của automation tester.

Ví dụ: TimeoutException: Expected condition failed: waiting for visibility of element located by By.id: flash (tried for 15 second(s) …).

Đào sâu: How do you capture a screenshot on failure? → TakesScreenshot trong @AfterMethod hoặc Listener, trước quit().

AC9. What role does automation play in CI/CD?

Dịch: Automation trong CI/CD đóng vai trò gì?

Sample answer: The pipeline runs the tests automatically on each change, usually a fast smoke suite on every commit and a fuller regression nightly or before release. Tests must run headless, be independent, and produce reports and artifacts such as screenshots. A failing test should block or alert, so tests must be stable enough to be trusted. The Maven Wrapper lets the pipeline use the same Maven version as developers.

Giải thích: Nêu điều kiện để chạy được trong CI: headless, độc lập, ổn định, có báo cáo.

Ví dụ: ./mvnw -B clean test (minh hoạ GitHub Actions ở 06-test-execution-and-reports).

Đào sâu: Tests pass locally but fail in CI — why? → scenario S7: khác JDK/browser/headless/kích thước cửa sổ/tốc độ.

AC10. What do you need for safe parallel execution?

Dịch: Cần gì để chạy song song an toàn?

Sample answer: Each test must be independent with its own data, and each thread needs its own WebDriver, typically through ThreadLocal<WebDriver>. I configure TestNG parallel and thread-count, avoid shared mutable static state, and make sure reports and logs are thread-aware. Parallelism exposes hidden dependencies between tests.

Giải thích: Song song làm lộ ra test phụ thuộc nhau và dữ liệu dùng chung.

Ví dụ: <suite parallel="classes" thread-count="3"> (TestNG mục 9).

Đào sâu: Why not a static WebDriver? → các luồng giẫm lên cùng một trình duyệt.

AC11. Selenium vs Playwright vs Cypress — how do they differ?

Dịch: So sánh Selenium, Playwright, Cypress.

Sample answer: Selenium implements the W3C WebDriver protocol, supports many languages and browsers, and has the largest ecosystem; waiting is mostly my responsibility through explicit waits. Playwright drives browsers directly with a modern API, has auto-waiting for actionability, web-first assertions that retry, isolated browser contexts, and tooling such as a trace viewer; it supports several languages including Java, TypeScript and Python. Cypress runs inside the browser, is JavaScript/TypeScript only, and has a great developer experience but different constraints for things like multiple tabs. My choice would depend on the team's language, browser needs and existing suite.

Giải thích: Đây là kiến thức chung của người soạn, chưa kiểm chứng ở thời điểm bạn phỏng vấn — hãy kiểm tra lại tài liệu chính thức của từng công cụ. Câu trả lời tốt là so sánh có tiêu chí, không "công cụ nào tốt hơn".

Ví dụ: Bạn có thể nói: "I'm solid on Selenium synchronization, so I understand why auto-wait exists, and I plan to rewrite my 10 Selenium exercises in Playwright to compare."

Đào sâu: What do you still need explicit waits for in Playwright? → các điều kiện nghiệp vụ không thuộc kiểm tra "actionability" mặc định (ví dụ chờ dữ liệu đổi sang giá trị cụ thể).

AC12. UI vs API automation: when do you use each? What is a hybrid approach?

Dịch: Khi nào UI, khi nào API; cách kết hợp?

Sample answer: I verify business rules and data at API level because it is faster and more stable, and use UI tests for critical user flows and rendering behavior. A hybrid approach uses API or database calls for setup and cleanup, for example creating a user or logging in by API, and the UI only for the step under test. That cuts runtime and flakiness.

Giải thích: Điểm mạnh của bạn (API/SQL) — hãy nói theo hướng này.

Ví dụ: 50 test cần đăng nhập (scenario S8): đăng nhập qua API/cookie thay vì UI cho mỗi test.

Đào sâu: Risks of skipping the UI login? → không kiểm tra được chính chức năng đăng nhập; vẫn cần ít nhất một test UI cho nó.

AC13. How do you handle different environments (dev, staging) and configuration?

Dịch: Xử lý nhiều môi trường và cấu hình?

Sample answer: I externalize base URL, browser, headless flag and timeouts into a properties file, and allow overrides with system properties, for example -Dbase.url=... and -Dheadless=true when running through Maven. Secrets come from environment variables, not from the repository. A Maven profile or separate config file per environment is an option for larger projects.

Giải thích: Cho thấy bạn tách "cấu hình" khỏi "code".

Ví dụ: Config.get(key, default) trong Lab 08: System.getProperty(k, P.getProperty(k, d)).

Đào sâu: Why must system properties reach the test JVM when using Maven? → Surefire fork JVM; cần cấu hình để truyền property (xem Lab 08, bảng lỗi thường gặp).

AC14. How do you keep automation maintainable? What do you check in code review?

Dịch: Giữ test dễ bảo trì; review code test kiểm tra gì?

Sample answer: Locators live in page classes, tests read like business steps, assertions stay in tests, and each test is independent and has one clear reason to fail. In review I look for fixed sleeps, absolute XPaths, hard-coded data, duplicated code, missing waits for the right condition, unclear names, and assertions without messages. I also agree with developers on stable attributes such as data-test-id.

Giải thích: Nêu checklist cụ thể.

Ví dụ: Checklist PR ở Git bài 03.

Đào sâu: A locator breaks every sprint. What do you do? → scenario S11.

AC15. What would you improve in your own project?

Dịch: Bạn sẽ cải thiện gì trong project của mình?

Sample answer: Today it runs 10 independent UI exercises with a shared BaseTest and explicit waits only. I would add Page Objects to remove locators from tests, move credentials and URLs into configuration, add a DriverFactory with headless support, take screenshots on failure, use @DataProvider for negative login cases, and run it in CI. I would also split tests that cover two features, like the dynamic controls test.

Giải thích: Trả lời trung thực, dựa trên phân tích thật (00-project-analysis mục 10–11) cho thấy bạn biết giới hạn của chính mình — điểm cộng lớn với Fresher/Junior.

Ví dụ: Các điểm trên khớp với "Những gì dự án CHƯA có" trong phân tích dự án.

Đào sâu: Which one first, and why? → POM + config (giảm chi phí bảo trì nhiều nhất), sau đó screenshot/CI.
