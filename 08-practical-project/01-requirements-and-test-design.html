1. Khái niệm

Automation không bắt đầu bằng code mà bằng câu hỏi: kiểm thử cái gì, vì sao, dữ liệu nào, kết quả mong đợi ra sao. Chuỗi suy nghĩ:

text
Requirement ─► Test Scenario (kịch bản ở mức cao) ─► Test Case (bước + dữ liệu + kết quả mong đợi)
            ─► Chọn cái nào tự động hoá ─► Test Script (Selenium)
Thuật ngữ Ý nghĩa Ví dụ
Requirement Điều hệ thống phải làm "Người dùng đăng nhập bằng tài khoản hợp lệ thì vào khu vực bảo mật"
Test Scenario Một tình huống cần kiểm tra "Đăng nhập thành công", "Đăng nhập sai mật khẩu"
Test Case Scenario cụ thể hoá: precondition, bước, dữ liệu, kết quả mong đợi TC_LOGIN_01
Traceability Bảng nối Requirement ↔ Test Case Đảm bảo không sót

2. Syntax: mẫu Test Case

Trường Nội dung
ID TC_<MODULE>_<số>
Tiêu đề Ngắn, nêu hành vi
Mức ưu tiên High / Medium / Low
Precondition Trạng thái ban đầu
Bước Các bước đánh số
Dữ liệu Input cụ thể
Kết quả mong đợi Quan sát được và kiểm chứng được
Tự động hoá? Có/Không + lý do

3. Ví dụ: phân tích các chức năng trong đề de.md

3.1. Requirement (rút từ 10 bài tập của dự án)

Mã Requirement (mô tả hành vi) Trang
R1 Đăng nhập hợp lệ vào khu vực bảo mật; sai thông tin bị từ chối với thông báo /login
R2 Có thể tích/bỏ tích checkbox /checkboxes
R3 Bảng dữ liệu hiển thị đúng thông tin từng hàng /tables
R4 Dropdown cho chọn tuỳ chọn /dropdown
R5 Hover hiện thông tin người dùng /hovers
R6 Thêm/xoá phần tử động /add_remove_elements/
R7 Nội dung tải thêm khi cuộn /infinite_scroll
R8 Modal quảng cáo xuất hiện và đóng được /entry_ad
R9 Kéo thả đổi chỗ hai khối /drag_and_drop
R10 Điều khiển động: remove/add checkbox, enable/disable input kèm thông báo /dynamic_controls

3.2. Test Scenarios và quyết định tự động hoá

Scenario Req Ưu tiên Tự động hoá? Lý do / rủi ro
S1 Đăng nhập thành công R1 High ✅ Smoke Luồng quan trọng, ổn định
S2 Đăng nhập sai mật khẩu/username R1 High ✅ (DataProvider) Nhiều dữ liệu, lặp lại
S3 Tích cả hai checkbox R2 Medium ✅ Ổn định
S4 Đọc 4 hàng bảng R3 Medium ✅ Dữ liệu cố định của trang
S5 Chọn từng tuỳ chọn dropdown R4 Medium ✅ Ổn định
S6 Hover từng ảnh R5 Low ✅ Cần chờ visibility
S7 Thêm rồi xoá phần tử R6 Medium ✅ Cần chờ biến mất
S8 Cuộn vô hạn R7 Low ✅ (cẩn thận flaky) Phụ thuộc sự kiện scroll (từng flaky ở Ex7)
S9 Modal quảng cáo R8 Low ✅ Có độ trễ hiển thị
S10 Kéo thả R9 Low ✅ (dễ flaky) HTML5 DnD
S11 Dynamic controls R10 High ✅ Điển hình cho Wait
S12 "Trông đẹp/dễ dùng" — — ❌ Chủ quan → kiểm thử thủ công

Tiêu chí chọn tự động hoá: lặp lại thường xuyên · ổn định · giá trị cao · kết quả mong đợi rõ ràng · chi phí bảo trì thấp. Không tự động hoá: kiểm tra một lần, UI thay đổi liên tục, đánh giá chủ quan.

3.3. Test Cases (trích)

ID Tiêu đề Ưu tiên Precondition Bước Dữ liệu Kết quả mong đợi
TC_LOGIN_01 Đăng nhập thành công High Ở /login 1. Nhập username 2. Nhập password 3. Bấm Login tomsmith / SuperSecretPassword! URL kết thúc /secure; thông báo chứa You logged into a secure area!
TC_LOGIN_02 Sai mật khẩu High Ở /login như trên tomsmith / wrong Ở lại /login; thông báo chứa Your password is invalid!
TC_LOGIN_03 Sai username High Ở /login như trên nobody / SuperSecretPassword! Thông báo chứa Your username is invalid!
TC_CHK_01 Tích cả hai checkbox Medium Ở /checkboxes Bấm để cả hai cùng được chọn (lưu ý checkbox 2 mặc định đã tích) — Cả hai isSelected() == true
TC_DYN_01 Remove checkbox High Ở /dynamic_controls Bấm Remove, chờ — Thông báo It's gone!; checkbox không còn
TC_DYN_02 Enable input High Sau TC_DYN_01 hoặc trang mới Bấm Enable, chờ — Thông báo It's enabled!; input enabled, gõ được

Cột "Kết quả mong đợi" phải kiểm chứng được bằng code (text, URL, trạng thái) — nếu không viết được assertion thì test case chưa đủ rõ.

4. Ứng dụng với dự án Selenium Maven (Real-world)

  • Mỗi @Test nên ánh xạ về một Test Case (tên method nêu hành vi: shouldRejectInvalidPassword).
  • Mã Test Case có thể ghi ở description của @Test hoặc Javadoc (dự án hiện dùng Javadoc mô tả yêu cầu mỗi Exercise).
  • Phân nhóm groups = {"smoke"} cho TC_LOGIN_01, TC_DYN_*; còn lại regression (TestNG groups).
  • Test độc lập: không để TC_DYN_02 phụ thuộc kết quả TC_DYN_01.

5. Lỗi thường gặp

Lỗi Hậu quả Cách tránh
Viết code ngay, không có test case Test không bám yêu cầu, sót case âm Viết scenario/test case trước
Kết quả mong đợi mơ hồ ("hiển thị đúng") Không viết được assertion Nêu text/URL/trạng thái cụ thể
Chỉ có case dương Bỏ lỡ bug xử lý lỗi Thêm case âm (sai mật khẩu, thiếu dữ liệu)
Tự động hoá mọi thứ Chi phí bảo trì cao Dùng tiêu chí chọn tự động hoá
Test phụ thuộc nhau Fail dây chuyền, khó debug Mỗi test tự chuẩn bị trạng thái
Hard-code dữ liệu nhạy cảm Rò rỉ Config/biến môi trường

  • A. Không khác
  • B. Case có bước, dữ liệu, kết quả mong đợi cụ thể
  • C. Scenario có code
  • D. Case không có kết quả
Xem đáp án

Đáp án: B. Scenario ở mức cao hơn.

Câu 2. Không nên tự động hoá?

  • A. Kiểm tra chủ quan "đẹp/dễ dùng"
  • B. Smoke login
  • C. Regression lặp lại
  • D. Case âm
Xem đáp án

Đáp án: A. Kiểm thử thủ công.

Câu 3. Kết quả mong đợi tốt là?

  • A. "Hiển thị đúng"
  • B. "Không lỗi"

💼 Interview Corner

1. How do you decide what to automate?

  • 🇻🇳 Dịch: Quyết định tự động hoá cái gì?
  • Suggested answer (EN): Repetitive, stable, high-value and regression-prone scenarios with clear expected results; not one-off checks, rapidly changing UI or subjective checks.
  • Giải thích (VI): Bắt đầu từ smoke.
  • Follow-up: How do you measure ROI?

2. What is traceability?

  • 🇻🇳 Dịch: Traceability là gì?
  • Suggested answer (EN): A mapping between requirements and test cases that shows coverage and gaps.
  • Giải thích (VI): Phát hiện thiếu test đăng nhập sai.
  • Follow-up: How do you keep it up to date?

📌 Lesson Summary

Kiến thức cần nhớ

  • Requirement → Scenario → Test Case → Script
  • Kết quả mong đợi phải assert được
  • Traceability tìm khoảng trống

Method / lệnh cần biết

  • Mẫu Test Case: ID, ưu tiên, precondition, bước, dữ liệu, mong đợi

Điểm dễ nhầm lẫn

  • Scenario ≠ Test Case
  • Tự động hoá mọi thứ ≠ tốt
  • Test phụ thuộc nhau
