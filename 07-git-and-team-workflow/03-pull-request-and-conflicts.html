1. Khái niệm

Conflict xảy ra khi Git không tự quyết được vì cùng một vùng file bị hai nhánh sửa khác nhau. Git đánh dấu vị trí để con người chọn.

Pull Request (PR) là đề xuất gộp một nhánh vào main trên GitHub/GitLab: có thảo luận, review, CI chạy test trước khi merge.

2. Syntax: đọc dấu hiệu conflict

text
<<<<<<< HEAD                          ← phiên bản của nhánh HIỆN TẠI
        <selenium.version>4.54.0</selenium.version>
=======                               ← ngăn cách
        <selenium.version>4.53.0</selenium.version>
>>>>>>> feature/a                     ← phiên bản của nhánh đang gộp vào

Các bước:

bash
git status                      # liệt kê file "both modified"
# 1. mở file, QUYẾT ĐỊNH nội dung đúng, XOÁ các dòng <<<<<<<, =======, >>>>>>>
# 2. kiểm chứng bằng build
.\mvnw.cmd clean test
git add pom.xml                 # đánh dấu đã giải quyết
git commit                      # (merge) hoặc: git rebase --continue (rebase)
# huỷ bỏ nếu rối:
git merge --abort               # hoặc: git rebase --abort

2.1. Từng dấu hiệu và lệnh khi xử lý conflict

Ba dòng đánh dấu <<<<<<<, =======, >>>>>>>

Dòng Nghĩa
<<<<<<< HEAD Bắt đầu vùng xung đột; phần ngay sau là phiên bản của nhánh bạn đang đứng
======= Ngăn cách hai phiên bản
>>>>>>> feature/a Kết thúc; phần ngay trước là phiên bản của nhánh đang được gộp vào
  • Nhiệm vụ của bạn: quyết định nội dung đúng (giữ một bên, giữ cả hai, hoặc viết lại) rồi xoá cả ba dòng đánh dấu.
  • Lưu ý: để sót dòng đánh dấu thì file hỏng (pom.xml không còn là XML hợp lệ). Kiểm tra: grep -rn "<<<<<<<" .

git status khi đang conflict

  • Làm gì: liệt kê file both modified (cả hai bên cùng sửa — cần bạn giải quyết) và cho biết đang ở giữa merge/rebase.
  • 🟢.

git diff --name-only --diff-filter=U

  • Làm gì: chỉ liệt kê tên các file còn conflict chưa giải quyết. 🟢.

git add <file> (sau khi sửa conflict)

  • Làm gì: báo cho Git "file này đã giải quyết xong". Chưa add thì Git vẫn coi là conflict.

git commit (khi đang merge) / git rebase --continue (khi đang rebase)

  • Làm gì: hoàn tất việc gộp sau khi mọi file đã add. Merge → commit gộp; rebase → tiếp tục áp commit kế tiếp.

git merge --abort / git rebase --abort

  • Làm gì: huỷ hẳn lần gộp đang dở, đưa mọi thứ về trạng thái trước khi bắt đầu. 🟡 — an toàn để bắt đầu lại khi bị rối.

git checkout --ours <file> / git checkout --theirs <file>

  • Làm gì: chọn nhanh một phía cho cả file khi không cần trộn.
  • Lưu ý: khi merge, --ours = nhánh bạn đang đứng; khi rebase, ý nghĩa đảo ngược (--ours = nhánh đích). Dễ nhầm nên thường sửa tay an toàn hơn.

2.2. Pull Request — các khái niệm

Thuật ngữ Nghĩa
Base (nhánh đích) Nhánh muốn gộp vào (thường main)
Compare (nhánh nguồn) Nhánh chứa thay đổi của bạn
Review Người khác đọc code; có thể Comment, Approve (đồng ý), Request changes (yêu cầu sửa)
CI check Kiểm tra tự động (chạy clean test) — nên xanh mới merge
Merge pull request Gộp vào base; có các kiểu: merge commit, squash (gom thành 1 commit), rebase and merge
Draft PR PR chưa sẵn sàng review

Một PR tốt: nhỏ (một mục đích), mô tả Mục đích – Thay đổi – Cách kiểm chứng, CI xanh, đã tự đọc lại diff trước khi mở.

3. Ví dụ (đã chạy thật)

Ví dụ 1 — Conflict thật ở pom.xml

Hai nhánh cùng đổi selenium.version; git merge feature/a báo:

text
CONFLICT (content): Merge conflict in pom.xml
Automatic merge failed; fix conflicts and then commit the result.

File pom.xml có đoạn (số dòng 19–23) đúng như khối ở mục 2. Cách quyết định: không chọn theo cảm tính — hỏi ai cần phiên bản nào, đọc ghi chú phát hành, chọn một giá trị, rồi clean test.

Ví dụ 2 — Conflict hai người cùng thêm dependency

xml
<<<<<<< HEAD
        <dependency> ... slf4j-simple ... </dependency>
=======
        <dependency> ... opencsv ... </dependency>
>>>>>>> feature/csv

Ở đây giữ cả hai (không xoá nhầm), bỏ ba dòng dấu hiệu, chạy dependency:tree rồi clean test (Dependency Management).

Ví dụ 3 — Quy trình một Pull Request

  1. git switch -c feature/page-object-login, code, commit nhỏ, rõ ràng.
  2. git push -u origin feature/page-object-login.
  3. Mở PR trên GitHub; mô tả: làm gì, vì sao, cách kiểm chứng (.\mvnw.cmd clean test → Tests run: N, Failures: 0, Skipped: 0).
  4. CI chạy test; reviewer nhận xét; sửa theo góp ý (commit thêm lên cùng nhánh).
  5. Approve → merge vào main → xoá nhánh.

Mẫu mô tả PR:

markdown
## Mục đích
Tách locator của trang Login vào LoginPage (POM).
## Thay đổi
- Thêm pages/BasePage, LoginPage, SecureAreaPage
- Thêm tests/LoginPomTest (2 test)
## Cách kiểm chứng
.\mvnw.cmd clean test  → Tests run: 12, Failures: 0, Errors: 0, Skipped: 0
## Lưu ý
Không đổi pom.xml.

4. Ứng dụng với dự án Selenium Maven (Real-world)

Checklist review code test (đầy đủ ở Maintainable Framework):

  • Assertion có ý nghĩa và có message?
  • Wait theo điều kiện, không Thread.sleep?
  • Locator ổn định, nằm trong Page?
  • Test độc lập, chạy lẻ được?
  • clean test xanh, Tests run đúng, Skipped: 0?
  • Không commit target/, .mvn/repository/, mật khẩu thật?
  • pom.xml đổi có lý do trong mô tả PR?

Hai file hay conflict: pom.xml (version/dependency) và testng.xml (danh sách class). Giữ cả hai thay đổi hợp lệ, rồi luôn chạy lại test.

5. Lỗi thường gặp

Lỗi Nguyên nhân Cách xử lý
Còn sót <<<<<<< trong file đã commit Không đọc lại grep -rn "<<<<<<<" . trước khi commit
Chọn một phía mà mất thay đổi của phía kia Xoá nhầm Đọc cả hai, giữ phần hợp lệ
Giải quyết xong nhưng build đỏ Gộp logic sai clean test, dependency:tree
PR quá lớn Khó review Chia nhỏ theo một mục đích
PR không nêu cách kiểm chứng Reviewer phải đoán Ghi lệnh + kết quả
git push bị từ chối sau rebase Lịch sử viết lại Hỏi nhóm; --force-with-lease chỉ trên nhánh cá nhân
Giải quyết conflict ngay trên main Rủi ro Giải quyết trên nhánh tính năng

💼 Interview Corner

1. How do you resolve a merge conflict in pom.xml?

  • 🇻🇳 Dịch: Giải quyết conflict ở pom.xml?
  • Suggested answer (EN): Read both sides, keep the valid changes from both, remove the markers, run dependency:tree and mvnw clean test, then commit.
  • Giải thích (VI): Đã chạy thật với selenium.version.
  • Follow-up: What if both changed the same version?

2. What do you check when reviewing test code in a pull request?

  • 🇻🇳 Dịch: Review code test cần kiểm tra gì?
  • Suggested answer (EN): Meaningful assertions, condition-based waits, stable locators, independent tests, no secrets, green clean test with the right test count and no generated files committed.
  • Giải thích (VI): Checklist.
  • Follow-up: What if CI fails but local passes?
