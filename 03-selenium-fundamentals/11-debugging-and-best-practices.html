1. Quy trình gỡ lỗi một test fail

  1. Đọc lỗi: exception, message, dòng code của bạn (09).
  2. Chạy lại một mình: .\mvnw.cmd test "-Dtest=Exercise07_InfiniteScrollTest" — pass lẻ nhưng fail cả bộ ⇒ test phụ thuộc/nhiễu.
  3. Chạy lại 3-5 lần: lúc pass lúc fail ⇒ flaky ⇒ nghi ngờ đồng bộ hoá.
  4. Quan sát: chạy có giao diện, nhìn Chrome làm gì; tạm thời Thread.sleep chỉ để xem (xoá sau).
  5. Kiểm tra locator trong DevTools ($$(), $x()).
  6. Thu thập bằng chứng: screenshot, getPageSource(), log.
  7. Sửa nguyên nhân gốc (Wait đúng điều kiện), không "vá" bằng sleep.
  8. Chạy lại nhiều lần để chắc đã hết flaky.

🧩 Ví dụ thật: Exercise07 từng gây TimeoutException (dấu vết: test-output/testng-failed.xml). Nguyên nhân gốc: sự kiện scroll bị bỏ qua khi plugin đang tải ⇒ sửa bằng custom wait có cuộn lặp — không phải tăng timeout.

2.1. Từng công cụ gỡ lỗi — cách dùng cụ thể

Chrome DevTools: $$("css")

  • Làm gì: gõ trong tab Console (F12): trả về mảng mọi phần tử khớp CSS selector.
  • Ví dụ: $$("#checkboxes input") → số phần tử và danh sách; trả về 0 phần tử nghĩa là locator sai.
  • Dùng để: kiểm tra locator trước khi đưa vào code, và kiểm tra tính duy nhất (chỉ nên ra 1 kết quả).

Chrome DevTools: $x("xpath")

  • Làm gì: như $$ nhưng dùng XPath.
  • Ví dụ: $x("//button[text()='Add Element']").

Chrome DevTools: tab Elements / Network / Console

Tab Cho biết
Elements Cây DOM hiện tại, thuộc tính, CSS của phần tử (đúng như Selenium thấy)
Console Lỗi JavaScript của trang; nơi thử $$/$x
Network Các request đang chạy — biết khi nào AJAX xong để chọn điều kiện Wait

Breakpoint trong IDE

  • Làm gì: đặt điểm dừng ở một dòng; khi chạy ở chế độ Debug, chương trình dừng tại đó để bạn xem giá trị biến, rồi chạy từng bước.
  • Lưu ý: trình duyệt vẫn mở khi dừng — nhìn trực tiếp trang đang ở trạng thái nào.

System.out.println / log

  • Làm gì: in giá trị ra console để theo dõi luồng chạy. Ví dụ: in getText() thực tế trước khi assert.
  • Lưu ý: không in mật khẩu. Dự án lớn nên dùng logger (SLF4J).

((TakesScreenshot) driver).getScreenshotAs(OutputType.FILE)

  • Làm gì: chụp ảnh phần trang đang hiển thị; trả về File tạm để bạn sao chép đi (xem mục 3).

driver.getPageSource()

  • Làm gì: trả HTML hiện tại của DOM — lưu ra file khi test fail để xem lại phần tử có tồn tại không.

-Dtest=Class#method

  • Làm gì: chạy riêng một test để cô lập lỗi, không bị các test khác ảnh hưởng.
Tình huống Công cụ đầu tiên
Không chắc locator đúng $$("css") / $x("xpath") trong Console
Phần tử "có mà không tìm thấy" Elements: có nằm trong iframe/shadow DOM?
Không biết khi nào trang sẵn sàng Network
Muốn xem trạng thái giữa chừng test Breakpoint
Fail trên CI không xem được Screenshot + getPageSource() + log

3. Screenshot khi test fail

java
import org.openqa.selenium.OutputType;
import org.openqa.selenium.TakesScreenshot;
import org.testng.ITestResult;

@AfterMethod
public void tearDown(ITestResult result) throws IOException {
    if (result.getStatus() == ITestResult.FAILURE && driver != null) {
        File src = ((TakesScreenshot) driver).getScreenshotAs(OutputType.FILE);
        Files.createDirectories(Path.of("target", "screenshots"));
        Files.copy(src.toPath(), Path.of("target", "screenshots", result.getName() + ".png"),
                   StandardCopyOption.REPLACE_EXISTING);
    }
    if (driver != null) driver.quit();
}

Gợi ý cải tiến (🧩 BaseTest hiện chưa chụp ảnh). Đặt vào target/ để không bị commit.

4. Log

Hiện dự án dùng System.out.println với thông tin trạng thái (hữu ích). Khi lớn hơn: SLF4J + Log4j2/slf4j-simple. Mỗi log nên nói đang làm gì và dữ liệu:

log.info("Click Add Element; số nút Delete hiện tại = {}", count);

5. Flaky test

Flaky = cùng code, cùng dữ liệu, lúc pass lúc fail.

Nguyên nhân Dấu hiệu Cách xử lý
Thiếu/Sai Wait NoSuchElement, Stale, Intercepted ngẫu nhiên Wait đúng điều kiện (05)
Phụ thuộc thứ tự/ dữ liệu chung Pass lẻ, fail chạy bộ Test độc lập; dọn dữ liệu
Môi trường (mạng, website chậm) Fail theo giờ Timeout hợp lý; mock/ môi trường ổn định
Animation Click vào chỗ đang di chuyển Chờ animation xong; tắt animation ở môi trường test
Thao tác khó (HTML5 drag) Ngẫu nhiên Phương án dự phòng (07)
Cửa sổ nhỏ/headless Phần tử bị che Đặt --window-size

⚠️ Retry tự động (rerunFailingTestsCount) chỉ che flaky; hãy tìm nguyên nhân.

6. Bảng Best Practices tổng hợp

Lĩnh vực Khuyến nghị 🧩 Dự án
Driver Khai báo WebDriver; quit() trong teardown ✅
Wait Explicit; không implicit; không sleep ✅
Locator id/data-testid/CSS > XPath; tập trung vào Page Object ◐ (chưa có POM)
Dữ liệu Không hard-code; dùng DataProvider/config ❌ hard-code
Assertion Có message; kiểm chứng trạng thái trước/sau ✅
Độc lập Mỗi test tự dọn ✅ (@BeforeMethod)
Báo cáo Screenshot + log khi fail ❌
Cấu hình Browser/URL/timeout từ file/-D ❌
Chạy CI chạy ./mvnw clean test (chưa có CI)
Song song ThreadLocal<WebDriver> ❌
Bảo mật Không commit mật khẩu thật ✅ (chỉ tài khoản demo công khai)

7. Checklist khi viết một test mới

  • Test có một mục tiêu rõ ràng, tên mô tả (testLoginSuccess).
  • Không phụ thuộc test khác.
  • Mọi bước bất đồng bộ đều có Wait theo điều kiện.
  • Assert có message mô tả.
  • Locator ổn định, kiểm tra trong DevTools.
  • Không có Thread.sleep.
  • Dữ liệu/URL là hằng số hoặc đọc từ config.
  • Chạy 3 lần liên tiếp đều pass.

8. Lỗi thường gặp của người mới

Lỗi Giải thích
Chỉ kiểm tra "không có exception" Test pass nhưng không kiểm chứng gì — phải Assert
Copy-paste locator tuyệt đối từ DevTools (/html/body/div[2]/...) Gãy khi layout đổi
Thread.sleep(5000) khắp nơi Chậm, vẫn flaky
Một test dài 100 bước Khó biết lỗi ở đâu; tách nhỏ
Dùng static WebDriver Không an toàn khi song song
Không dọn trình duyệt Process mồ côi
Bỏ qua test fail "vì flaky" Mất niềm tin vào bộ test

💼 Interview Corner

1. Walk me through debugging a failing UI test.

  • 🇻🇳 Dịch: Mô tả cách debug một test UI fail.
  • Suggested answer (EN): Read the exception and my first stack frame, rerun the single test several times, check the locator in DevTools, collect evidence like a screenshot, fix the root cause usually synchronization, and rerun repeatedly.
  • Giải thích (VI): Nêu quy trình có hệ thống.
  • Follow-up: How do you tell flaky from broken?

2. What causes flaky tests?

  • 🇻🇳 Dịch: Nguyên nhân flaky?
  • Suggested answer (EN): Missing or wrong waits, test dependencies, environment slowness, animations and window size differences.
  • Giải thích (VI): Chỉ xử lý được khi hiểu nguyên nhân.
  • Follow-up: Is retry a solution?

📌 Lesson Summary

Kiến thức cần nhớ

  • Debug có quy trình; thu bằng chứng
  • Flaky thường do đồng bộ hoá
  • Chụp ảnh trước quit()

Method / lệnh cần biết

  • TakesScreenshot, getPageSource, -Dtest=Class#method, ITestResult

Điểm dễ nhầm lẫn

  • Flaky ≠ hỏng
  • Retry ≠ sửa
  • Pass lẻ ≠ độc lập

java
public final class Screenshots {
    private Screenshots() {}

    public static Path take(WebDriver driver, String name) {
        try {
            File src = ((TakesScreenshot) driver).getScreenshotAs(OutputType.FILE);
            Path dir = Path.of("target", "screenshots");
            Files.createDirectories(dir);
            return Files.copy(src.toPath(), dir.resolve(name + ".png"), StandardCopyOption.REPLACE_EXISTING);
        } catch (IOException e) {
            throw new UncheckedIOException(e);
        }
    }
}
